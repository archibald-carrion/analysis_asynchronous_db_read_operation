# How the Experiment Works (flow + TPC-H explained)

This is the "what is actually happening" companion to `SETUP_AND_RUN.md`. It walks the
experiment from the outermost orchestrator down to a single query, and explains the **TPC-H**
concept behind each step so you can read the code and the results without re-learning TPC-H.

> **One-line summary:** the experiment runs a **TPC-H–derived** workload (Power test +
> Throughput test → QphH) against PostgreSQL 18, **once per cell** of a Completely Randomized
> Design that crosses **3 I/O methods × 4 DB sizes × 12 replicates = 144 runs**, to compare
> `sync` vs `bgworkers` vs `io_uring`.
>
> Compliance caveat: this is **TPC-H–derived**, not an audited TPC-H result (no answer-set
> verification). See `TPCH_COMPLIANCE.md` for the clause-by-clause audit.

---

## 0. TPC-H in one screen

TPC-H is a decision-support benchmark. It defines:

- **Schema & data** — 8 tables (`region`, `nation`, `supplier`, `customer`, `part`,
  `partsupp`, `orders`, `lineitem`), populated by **`dbgen`**. The volume is set by a
  **Scale Factor (SF)** ≈ GB of raw data (SF=1 → ~1 GB, `orders` has SF × 1,500,000 rows).
- **22 queries (Q1–Q22)** — fixed analytical SQL, generated by **`qgen`** with random
  substitution parameters per stream.
- **2 refresh functions** — **RF1** inserts a batch of new `orders`+`lineitem` rows; **RF2**
  deletes an equivalent batch. They simulate the DB changing under load. The data for them
  comes from `dbgen -r` (the `dss.ri` insert set and `dss.rd` delete set).
- **Two tests:**
  - **Power test** — single stream, measures raw speed: `RF1 → 22 queries → RF2`.
  - **Throughput test** — `S` query streams run **concurrently** with one refresh stream,
    measures total work over wall-clock time `Ts`.
- **The metric — QphH@Size** (Queries-per-Hour) = geometric mean of the two tests:
  `QphH = sqrt(Power@Size × Throughput@Size)`. Higher is better.

Everything below is the machinery that produces one QphH number per run, 144 times.

## 1. The layers (call graph)

```
run_full_experiment.sh         ← optional all-in-one: (re)build DBs + schedule + run
   │
   ├─ run_setup.sh             ← per scale: build tpch-kit, dbgen data, qgen queries, load DB
   ├─ generate_experimental_design.py   ← writes the randomized CRD schedule CSV
   └─ run_randomized_experiment.sh      ← the experiment driver (reads the schedule)
         │   for each row of the schedule (randomized order):
         ├─ toggle_pg_config.sh <method>   ← swap postgresql.conf, set io_method
         ├─ restart PostgreSQL + drop OS caches + cooldown
         └─ run_tests.sh <method>          ← ONE TPC-H run → one QphH
               ├─ execute_power_test        RF1 → 22 Q (stream 0) → RF2
               ├─ execute_throughput_test   S query streams ∥ refresh stream, timed
               └─ calculate_qphh            geomean math → QphH@Size
```

You normally invoke **one** of two entry points:
- `run_randomized_experiment.sh` — databases already built (the common case).
- `run_full_experiment.sh` — also (re)builds everything from scratch first.

---

## 2. Setup phase — `run_setup.sh` (once per scale factor)

Run once per DB size. For `SCALE_FACTOR=10 DB_NAME=tpch_db_10gb ./run_setup.sh` it:

1. **Builds tpch-kit** (`dbgen`, `qgen`) with `MACHINE=LINUX DATABASE=POSTGRESQL`.
2. **Generates data** — `dbgen -s 10` writes the `*.tbl` files (the 8 tables).
3. **Generates refresh data** — `dbgen -r 1` writes **`dss.ri`** (rows RF1 will insert) and
   **`dss.rd`** (keys RF2 will delete). *These are mandatory* — without them a run aborts
   (see §6).
4. **Creates the role/DB** — `tpch_user` / `tpch_password_123`, database `tpch_db_10gb`,
   schema, then `\copy` loads the `*.tbl` data.
5. **Generates the queries** — `qgen` produces Q1–Q22. Crucially it writes **per-stream sets**
   with distinct RNG seeds:
   - `tpch_queries_sf10/stream0/q1..q22.sql` — the Power-test stream (seed-derived params)
   - `tpch_queries_sf10/stream1..streamN/` — one set per Throughput stream
   - This is the TPC-H rule that **each stream uses different substitution parameters**.
   - A `LIMIT -1` / stray-semicolon fixup is applied to every generated file.

> **TPC-H tie-in:** steps 2–3 are *data population*; step 5 is the *query set*. The per-stream
> directories are why streams aren't all running the identical parameterized query.

---

## 3. Design phase — `generate_experimental_design.py`

Produces `experimental_design_schedule.csv`, the **master plan and results table**. It is a
**Completely Randomized Design (CRD)**:

- **Factors:** I/O method (`sync`, `bgworkers`, `iouring`) × DB size (e.g. `0.1, 1, 10, 40`).
- **Replicates:** 12 per treatment → `3 × 4 × 12 = 144` runs.
- **Randomized order** — runs are shuffled so time-correlated noise (thermal drift, background
  load) doesn't confound any one treatment. Each row carries `status` (PENDING/COMPLETED/
  FAILED) and empty result columns (`qphh_result`, …) that the driver fills in.

> **Why CRD, not TPC-H:** TPC-H defines *one* benchmark execution. The CRD is *our* statistical
> wrapper around it — repeating the TPC-H run many times under controlled, randomized
> conditions so we can compare the three I/O methods with replication.

---

## 4. Driver phase — `run_randomized_experiment.sh`

This is the experiment loop. Once (`main`): checks the schedule, verifies prerequisites
(scripts present, PostgreSQL up, every database in the schedule exists, disk space), asks for
confirmation + shows an ETA. Then, for **each schedule row in randomized order** (`execute_run`):

1. **`switch_database`** — point the next run at the right `tpch_db_<n>gb`.
2. **`configure_io_method` → `toggle_pg_config.sh <method>`** — swap in the
   `sync`/`bgworkers`/`iouring` postgresql.conf (this is where `io_method=io_uring` is actually
   set). *This* is the independent variable being manipulated.
3. **`restart_postgresql`** — apply the conf and start from a clean server state.
4. **`clear_caches`** — `sync` + `echo 3 > /proc/sys/vm/drop_caches` so every run starts
   cold (no OS page-cache carryover — important when the whole point is *I/O* behavior).
5. **Cooldown** — sleep N minutes to let the machine settle.
6. **Run the benchmark** — export `IO_METHOD/DB_NAME/SCALE_FACTOR`, `ITERATIONS=1`,
   `RUNS_PER_ITERATION=1`, `SKIP_POSTGRES_RESTART=1` (the driver already restarted), then call
   `run_tests.sh <method>`. Output streams to `run_<order>_<treatment>_rep<n>.log`; errors-only
   to the sibling `.errors.log`.
7. **Collect results** — move `tpch_*_results.csv` into `randomized_results/raw_data/`,
   compute QphH, and **write it back into the schedule row** with status `COMPLETED`
   (or `FAILED`).

Key properties:
- **Resumable** — COMPLETED rows are skipped on re-run; FAILED rows are retried. Safe to
  Ctrl-C and restart.
- **A run can "complete" with internal failures.** If individual queries/RFs failed (logged as
  warnings), the `.errors.log` is non-empty and the driver warns you — don't trust a QphH
  whose run left a non-empty errors log. A clean run deletes its empty errors log.

> **TPC-H tie-in:** steps 2–5 are *experimental hygiene* (our additions for a fair I/O
> comparison), not TPC-H. Step 6 is where the actual TPC-H run happens.

---

## 5. One TPC-H run — `run_tests.sh` (the core)

Called once per schedule row. `main()` does setup → power test → throughput test → metric.

### 5a. Run setup
- `test_postgres_connection` — fail fast if the DB isn't reachable.
- `detect_scale_factor_from_db` — recompute SF from the data:
  `SF = COUNT(*) FROM orders / 150000`. (Self-correcting: the metric uses the *real* SF.)
- **`auto_set_query_streams`** — pick `S` from the **official TPC-H minimum-streams table**
  (Clause 5.4.1.2), not a guess: SF≤1→**2**, 10→**3**, 30→**4**, 100→**5**, 300→**6**, 1000→**7**…
  For this study: SF 0.1 & 1 → S=2, SF 10 → S=3, SF 40 → S=4.
- `select_queries_dir` — choose `tpch_queries_sf<tag>/` (per-stream sets) or fall back to the
  flat `tpch_queries/`.
- **`ensure_refresh_files`** — assert `rf1.sql`, `rf2.sql`, `dss.ri`, `dss.rd` all exist, or
  **abort** (no silent skip → no fake `0.00` QphH).

### 5b. Power test — `execute_power_test` (single stream, "how fast")
TPC-H sequence, executed on **stream 0**:
1. **RF1** (`execution_order` 1) — insert the `dss.ri` batch.
2. **All 22 queries** in a randomized order (Fisher–Yates shuffle — TPC-H permits ordering).
   Each uses the **stream 0** parameter set.
3. **RF2** (`execution_order` 24) — delete the `dss.rd` batch.

Produces **24 timings** (22 queries + RF1 + RF2). Each query/RF is timed with `date +%s.%N`
around a `psql -f`; results go to `tpch_complete_results.csv` / `tpch_refresh_results.csv`.

### 5c. Throughput test — `execute_throughput_test` (concurrent, "how much")
- Launches **`S` query streams as parallel background processes**; each runs all 22 queries
  in its own random order, using its **own** parameter set (`stream1..streamS`).
- Launches **one refresh stream** that issues RF1/RF2 pairs in a loop until all query streams
  finish.
- **`Ts`** = wall-clock from first stream start to last stream end → `tpch_interval_results.csv`
  (along with `stream_count = S`).

> **Why concurrency matters here:** the Throughput test is where async I/O (`io_uring`,
> `bgworkers`) is expected to pay off — many streams issuing reads at once is exactly the
> workload those methods optimize. The Power test is the single-stream baseline.

### 5d. The metric — `calculate_qphh` / `generate_response_variable_csv`
With SF, the 24 power timings, `S`, and `Ts`:

```
geomean      = exp( Σ ln(tᵢ) / 24 )            # over the 24 power timings
Power@Size   = (3600 × SF) / geomean
Throughput@Size = (S × 22 × 3600) / Ts
QphH@Size    = 1 / sqrt( (1/Power) × (1/Throughput) )   # = sqrt(Power × Throughput)
```

Guarded: it requires **exactly 22 query + 2 RF** power timings and a valid `Ts`/`S`, else it
returns `0.00`. So a `0.00` means "this run is invalid," not "slow." The driver writes the
result into the schedule's `qphh_result` column.

## 6. Failure modes & how you'll see them

| Symptom | Meaning | Where to look |
|---|---|---|
| Run aborts at setup with "Missing required refresh artifact" | `dss.ri`/`dss.rd` not generated | re-run `run_setup.sh` for that scale (`dbgen -r 1`) |
| `qphh_result = 0.00` + non-empty `.errors.log` | queries/RFs failed → not 24 valid timings | `randomized_results/logs/run_*.errors.log` (has the real Postgres error) |
| `SHOW io_method;` errors / iouring won't start | PostgreSQL build lacks io_uring | use PGDG `postgresql-18` (see `SETUP_AND_RUN.md` Step 2) |
| Schedule row stuck `FAILED` | run errored; will be retried on next invocation | full log `run_*.log` |

The **errors-only log** is the fast path: clean runs leave it empty (and it's auto-deleted),
so any `.errors.log` present in `randomized_results/logs/` flags a run to inspect.
