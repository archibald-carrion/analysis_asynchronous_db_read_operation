# TPC-H Compliance Audit

**Scope:** This document audits how faithfully the benchmark in this repository implements
the TPC-H specification. It is a *methodological* audit for the paper, **not** an official
TPC audit — these results are not auditable/publishable as official TPC-H QphH numbers
(no TPC sponsor, no audited answer-set verification). The intent is to let the paper
describe the workload honestly as a **TPC-H–derived benchmark**.

**Audited files:** `run_tests.sh`, the per-scale generated query sets
(`tpch_queries_sf<tag>/stream*/q1..q22.sql`), the hand-authored refresh SQL
(`templates/rf1.sql`, `templates/rf2.sql`), `run_setup.sh`, `run_randomized_experiment.sh`.

## 1. Database population & scale

- Data is generated by **tpch-kit `dbgen`** and loaded via `\copy` with `DELIMITER '|'`
  (`run_setup.sh`). Scale factors used: 0.1, 1, 10 (GB-equivalent).
- Scale factor is taken from the explicit `SCALE_FACTOR` passed to `run_tests.sh` (set by the
  harness per database). An earlier run-time auto-detection (`rows(orders) / 150000`) used the
  wrong divisor — TPC-H `orders` cardinality is `SF × 1,500,000`, so it reported SF=1.0 for the
  100 MB database and selected the wrong query/refresh set — and was **removed** in favor of
  trusting the explicit factor.

**Verdict:** ✅ Compliant. Tables and cardinalities come from the reference generator.

### 1.1 Toolchain provenance (why tpch-kit, not the raw V3.0.1 download)

The data/query generator used by `run_setup.sh` is **tpch-kit** (`gregrahn/tpch-kit`,
cloned and built with `MACHINE=LINUX DATABASE=POSTGRESQL`), **not** the dbgen/qgen shipped
inside the official *TPC-H Tools v3.0.1* download. This is a deliberate, documented choice:

- **tpch-kit is the same official TPC source, ported — not a different benchmark.** It
  carries the TPC dbgen/qgen C sources with the minimal patches required to (a) compile on
  modern **Linux** and (b) emit **PostgreSQL**-compatible output. The data-generation and
  substitution-parameter logic is unchanged; the generated `.tbl` data, `dss.ri`/`dss.rd`
  refresh sets, and Q1–Q22 are the reference TPC-H artifacts.
- **The official v3.0.1 source cannot build for this stack as shipped.** Its `makefile.suite`
  exposes only legacy `MACHINE` values (ATT, DOS, HP, IBM, ICL, MVS, …) with **no `LINUX`**,
  and `tpcd.h` provides database branches only for INFORMIX / DB2 / Teradata / SQL Server /
  Vectorwise — **no PostgreSQL**. Building it for Postgres-on-Linux would mean re-implementing
  exactly the port tpch-kit already provides, with a real risk of subtly diverging load
  formats or RF semantics.
- **The official download remains the authority for the spec and reference data.** This repo
  uses the v3.0.1 `specification.pdf`/`.docx` as the canonical specification, and the
  download's `ref_data/<SF>/` per-scale reference datasets and delete/update sets are
  available as an *external* validation reference. tpch-kit does not ship `ref_data/`; the
  official download is the correct source for any answer-set / refresh-set cross-check.

**Net:** generator = tpch-kit (the only Linux+PostgreSQL-buildable form of the official
dbgen/qgen); specification + reference data authority = official TPC-H Tools v3.0.1. This
keeps generation reproducible on the target platform while preserving an authoritative
reference for validation. (Result-set correctness verification against `ref_data/` is still
not performed — see §4/§5 — and is disclosed as a limitation.)

**Generator version & pinning (Clause 4.2.1.3).** Clause 4.2.1.3 (via TPC Policies 5.3.1)
makes it the sponsor's responsibility to ensure the DBGEN version corresponds to the
specification revision in use. The spec revision targeted here is **3.0.1**; the generator
is gregrahn/tpch-kit, whose dbgen self-reports internal version **2.17.3**. These are not
mismatched: "2.17.3" is the dbgen C-source version line (the official tree is at 2.x), while
"3.0.1" is the *specification document* revision — the two are numbered independently, and
the data-generation and refresh-set (RF1/RF2) semantics are unchanged across the 2.18 → 3.0.1
range, so this dbgen produces the artifacts the 3.0.1 spec defines. To discharge the
"sponsor's responsibility" reproducibly, `run_setup.sh` **pins tpch-kit to a fixed commit**
(`TPCH_KIT_COMMIT=852ad0a5ee31ebefeed884cea4188781dd9613a3`) rather than floating `HEAD`:
the clone checks out that exact SHA, re-running setup re-pins instead of `git pull`-ing
forward, and the pinned short SHA is logged on every run so each result set is stamped with
the generator that produced it. Because this is a TPC-H–*derived* research benchmark and not
an audited submission, the third-party fork is acceptable; the pin + version stamp is what
makes the generator provenance defensible.

## 2. Query set (Q1–Q22)

- The generated `q1.sql … q22.sql` (under `tpch_queries_sf<tag>/stream*/`) are genuine
  **`qgen` output** (the generator header is preserved in each file).
- `LIMIT` clauses match the spec where required (e.g. Q2 `limit 100`, Q3 `limit 10`,
  Q18 `limit 100`).
- Executed via `psql -f` in `execute_query` (`run_tests.sh:118`).

**Verdict:** ✅ Compliant. Queries are unmodified reference SQL.

⚠️ **Deviation 2a — single parameter set.** `qgen` was run once, so every stream/iteration
executes the **same** substitution parameters. TPC-H expects validation-distinct parameters
per stream.

✅ **Status after fixes.** `run_setup.sh` now generates one query set **per stream** with a
distinct deterministic qgen RNG seed (`generate_query_set`, seed `1000 + stream_index`),
laid out as `tpch_queries_sf<tag>/stream0/ … streamN/`. `run_tests.sh execute_query` selects
`$QUERIES_DIR/stream${stream_id}/q${n}.sql` (POWER = stream0; THROUGHPUT = stream1..S),
falling back to the flat set if per-stream dirs are absent. Streams now use distinct
parameters per spec. (Answer-set *correctness* verification is still not performed — see 4/5.)

## 3. Refresh functions (RF1 / RF2)

A single, spec-faithful implementation exists per refresh function:

| File | What it does |
|---|---|
| `rf1.sql`, `rf2.sql` | Insert/delete using dbgen refresh data sets (`dss.ri.orders.k` / `dss.ri.lineitem.k` for RF1, `dss.rd.k` for RF2) via `\copy` |

**Which runs:** `execute_refresh_function` calls `rf${n}.sql` with a **set number**; it stages
that set's data files and hard-errors if they (or the required number of sets) are missing
(`ensure_refresh_files` + `execute_refresh_function`).

- RF1 inserts the dbgen-generated new orders + line items; RF2 deletes the
  dbgen-provided order keys — matching the TPC-H RF1/RF2 definitions
  (Clauses 2.6/2.7) and the "data set produced by DBGen" requirement (Clauses 2.6.3/2.7.3).
  Row volume target is `SF × 1500` orders.

⚠️ **Deviation 3a — silent skip risk (resolved).** Earlier the tree also carried
synthetic `rf1_fixed.sql`/`rf2_fixed.sql` (fabricated values via `RANDOM()`/`TABLESAMPLE`)
that were **never executed** — dead code that misrepresented the active path. They have been
**removed**; only the spec-faithful `dss.*` loaders remain. The remaining historical risk was
the opposite: if `dss.*` were missing, RF was once **silently skipped**, leaving < 24 power
timings and a `0.00` QphH rather than a clear failure.

✅ **Status after fixes.** RF execution is now **mandatory and fail-loud**: `ensure_refresh_files`
asserts `rf1.sql`, `rf2.sql` and the numbered refresh data sets exist (else `error` → abort), and
`execute_refresh_function` calls `error` (not a silent skip) if a set's data is missing.
A run can no longer produce an invalid `0.00` QphH from absent refresh data. The synthetic
`_fixed` variants no longer exist in the tree, so there is exactly one RF implementation.

⚠️ **Deviation 3b — single refresh set reused (resolved).** Earlier `run_setup.sh` generated
only **one** refresh set (`dbgen -U 1`) and every RF1 reused it. Because RF1 is insert-only
(Clause 2.6.2), the **second** RF1 of a run re-inserted keys the first RF1 already added,
violating `pk_orders` (`ERROR 23505: duplicate key ... (o_orderkey)`). The power test passed
(one pair) but the throughput test failed on its first RF1.

> **Clause 2.6.3 (RF1 data set):** *"The set of rows to be inserted must be produced by DBGen
> using the -U option. This option will produce as many sets of rows as required for use in
> multi-stream tests."* Clause 2.7.3 says the same for RF2's delete keys.

✅ **Status after fixes.** `run_setup.sh` now runs `dbgen -U N` with **N sized to the whole
experiment** for the DB: `N = (1 + S) × (runs + safety)`, **S** = stream count for the scale
(spec Table 11; see §6). It splits each dbgen set *k* into `dss.ri.orders.k` /
`dss.ri.lineitem.k` / `dss.rd.k` (trailing-pipe stripped) and records the count in `dss.nsets`.
`execute_refresh_function` takes a **set number** and stages that set's files for `\copy`. Set
numbers come from a **persistent per-DB counter** (`dss.next_set`, `next_refresh_set` in
`run_tests.sh`): each run allocates the next `1 + S` unused sets (1 power + S throughput), and the
counter advances across runs (endless reuse, §9). No set index is ever reused, so no RF1 ever
re-inserts another RF1's keys → no PK collision. This matches Clauses 2.6.3 / 2.7.3 and the
per-pair set usage of Clause 2.8.1.

> **Implementation note (`\copy` constraint).** psql's client-side `\copy` cannot interpolate
> `-v` variables, and server-side `COPY FROM PROGRAM` requires `pg_execute_server_program`
> (which `tpch_user` lacks). So `rf1.sql`/`rf2.sql` reference the data by **fixed relative
> path**, and `run_tests.sh` stages the chosen set into a private temp dir and runs `psql`
> with that dir as its working directory. The trailing `|` dbgen appends to every row is
> stripped at setup time (else `COPY` rejects rows: *"extra data after last expected column"*).

## 4. Power test

`execute_power_test` (`run_tests.sh:269`):
1. RF1 (execution_order 1)
2. All 22 queries on **stream 0**, order shuffled by `generate_random_order` (Fisher–Yates)
3. RF2 (execution_order 24)

**Verdict:** ✅ Compliant. The RF1 → 22 queries → RF2 single-stream sequence is the TPC-H
power test. (Query *order* is randomized, which the spec permits.)

## 5. Throughput test

`execute_throughput_test`:
- Launches **S parallel query streams** (`QUERY_STREAMS`), each running all 22 queries in a
  randomized order, as background processes.
- Runs a **parallel refresh stream** issuing **exactly S RF1/RF2 pairs** — one per query
  stream — each using a **distinct** refresh set (the S sets after this run's power-test set,
  allocated from the persistent per-DB counter; see §3/§9).
- Measurement interval `Ts` is wall-clock from first stream start to last stream end,
  written to `tpch_interval_results.csv`.

**Verdict:** ✅ Compliant (concurrent query streams + concurrent refresh stream, timed by
measurement interval; one distinct RF pair per stream per Clause 2.8.1).

> **Deviation 5a — bounded vs. continuous refresh stream (resolved).** The refresh stream
> previously ran RF1/RF2 in an **unbounded loop** until the query streams finished, which both
> (a) re-used the single refresh set → PK collision (see §3, Deviation 3b) and (b) is not what
> Clause 2.8.1 prescribes. Per Clause 2.8.1, *"a test sponsor running five streams would
> execute one RF1/RF2 pair during the power test … the throughput test would then execute the
> next five RF1/RF2 pairs."* The refresh stream now runs **exactly S pairs**, one per query
> stream, matching the clause.

## 6. Number of query streams (S)

⚠️ **Note 6a (original).** `auto_set_query_streams` set `S = max(1, floor(SF))`, a monotonic
proxy that did **not** reproduce the TPC-H S-per-SF table values.

✅ **Status after fixes.** `auto_set_query_streams` now uses the official TPC-H minimum-stream
table (SF≤1→2, 10→3, 30→4, 100→5, 300→6, 1000→7, …), picking the S for the largest band not
exceeding the actual SF. For this study: SF 0.1 & 1 → **S=2**, SF 10 → **S=3**, SF 40 → **S=4**.
`stream_count` is recorded in `tpch_interval_results.csv`, so the QphH throughput term stays
consistent.

## 7. QphH metric

`calculate_qphh` (`run_tests.sh:414`), confirmed against the spec:

- Geometric mean over the **24** power-test timings (22 queries + RF1 + RF2):
  `geomean = exp( Σ ln(tᵢ) / 24 )` (`run_tests.sh:485`).
- `Power@Size = (3600 × SF) / geomean` (`run_tests.sh:488`).
- `Throughput@Size = (S × 22 × 3600) / Ts × SF` (`run_tests.sh:540`) — matches spec
  Clause 5.4.2.1 verbatim **after the 2026-06-13 fix** (the `× SF` factor was previously
  omitted; see §8 #tp).
- `QphH@Size = 1 / sqrt( (1/Power) × (1/Throughput) )` (`run_tests.sh:547`)
  — algebraically equal to `sqrt(Power × Throughput)`, the TPC-H composite metric of
  Clause 5.4.3.1.

**Verdict:** ✅ Formula-correct (verified against spec Clauses 5.4.1/5.4.2/5.4.3). Guarded
against missing data (requires exactly 22 query + 2 RF timings, else returns `0.00`).

## 9. Database evolution across runs (Clause 2.8 / 2.8.1) — compliant (endless reuse)

TPC-H Clause 2.8 ("Database Evolution Process") governs database state **across runs** of the
performance test:

> **Clause 2.8:** *"The test sponsor must assure the correctness of the database for each run
> within the performance test. This is accomplished by 'evolving' the test database, keeping
> track of which set of inserted and deleted rows should be used by RF1 and RF2 for each run."*
>
> **Comment:** *"It is explicitly not permitted to rebuild or reload the test database during
> the performance test."*
>
> **Clause 2.8.1:** *"The test database may be endlessly reused if the test sponsor keeps
> careful track of how many pairs of refresh functions RF1/RF2 have been executed … one
> RF1/RF2 pair during the power test … the next five RF1/RF2 pairs [in the throughput test] …
> The next run would use the sets … for the seventh RF1/RF2 pair, and continue from there."*

Because RF1 inserts and RF2 deletes, a run **mutates** the database. We follow the spec's model
directly: the database is **reused in place and evolves; it is never reloaded or reset** between
runs. Correctness is guaranteed by a global, per-database refresh-set counter that advances one
RF1/RF2 set per pair, exactly as Clause 2.8.1 prescribes.

### Implementation (endless reuse + counter)

- **Set pool.** `run_setup.sh` generates `N = (1 + S) × (runs against that DB + safety)` distinct
  DBGen `-U` sets per scale (the run count is read from `experimental_design_schedule.csv` by
  `db_name`; `SET_SAFETY_RUNS`, default 2, absorbs FAILED-run retries). For the 36-runs-per-DB
  design that is **114 sets** for SF 0.1 / 1 (S=2) and **152 sets** for SF 10 (S=3). Each set is
  ~0.1% of the tables, so the whole pool is tiny on disk.
- **Counter.** `run_tests.sh` keeps a persistent per-DB counter `dss.next_set` in the scale's
  query dir (survives across the once-per-run `run_tests.sh` invocations). `next_refresh_set`
  hands out the next unused index and advances it. Each run allocates `1` set for the power test
  and `S` sets for the throughput test (allocated **before** forking the parallel streams so the
  counter is only ever written serially). So run #1 uses sets 1..(1+S), run #2 uses the next
  block, and so on — no set index is ever reused, and **no RF1 re-inserts an existing key**
  (the `pk_orders` collision that the old per-run reset and the earlier single-set bug both
  risked cannot occur).
- **No reload.** There is no `CREATE DATABASE … TEMPLATE`, no `<db>_tmpl`, and no per-run drop /
  recreate. `run_randomized_experiment.sh` simply points each run at the (evolving) database.

This is **fully compliant with Clause 2.8 / 2.8.1**: the DB is endlessly reused, never reloaded,
with careful tracking of how many RF1/RF2 pairs have executed.

### Trade-off (threat to validity)

Endless reuse means the database **evolves across runs** — run #1 and run #36 operate on slightly
different data (old rows deleted, new rows inserted at the advancing key frontier). For a
*comparative* study of I/O methods this introduces a small **nuisance factor**: a QphH difference
could in principle reflect the accumulated data state rather than the io_method. Two things bound
it: (a) each RF1/RF2 pair changes only ~0.1% of the tables and nets cardinality back to baseline,
so total drift over the experiment is small relative to table size; and (b) the **randomized run
order** (CRD) distributes any drift effect roughly evenly across the three io_methods rather than
confounding it with one. This is the standard TPC-H operating model and is disclosed in the
paper's threats-to-validity (replacing the previous "per-run reset" deviation note).

> **History.** Earlier revisions reset the DB to a pristine template before every run (only `1+S`
> sets needed, every run byte-identical). That avoided DB drift but was a disclosed **deviation**
> from Clause 2.8 ("do not rebuild/reload / evolve with a counter"), doubled on-disk size per
> scale, and cost ~30 min per run at 30 GB for the `CREATE DATABASE … TEMPLATE` copy. It was
> removed in favor of the spec-exact endless-reuse model above.

## 10. Conclusion

The benchmark is a **faithful TPC-H–derived implementation**: reference schema, reference
Q1–Q22, correct power/throughput sequencing, a correct QphH formula, and — after the
2026-06-13 and 2026-06-16 fixes — **distinct per-stream query parameters**, the **official
S-per-SF stream counts**, **guaranteed refresh-function execution** (fail-loud, never silently
skipped), a **distinct DBGen refresh set per RF1/RF2 pair**, and **spec-exact cross-run database
evolution** (Clause 2.8.1 endless reuse: the DB is reused in place and never reloaded, with a
persistent per-DB set counter handing each RF pair a fresh, never-reused set — no PK collisions;
see §9). Each individual run is a complete, valid TPC-H power+throughput test. It is suitable for
a *comparative* study of PostgreSQL I/O methods (sync / bgworkers / io_uring), which is the
paper's goal.

One disclosed limitation remains, reported in the paper's threats to validity, plus one
benign nuisance factor:

1. **No answer-set correctness verification (§4/§5).** There is no TPC sponsor and no
   result-set validation against official `ref_data/`.
2. **Cross-run database evolution (nuisance factor, not a deviation).** Under endless reuse the
   DB evolves across runs, so runs operate on slightly different data (~0.1% drift per RF pair,
   netting back to baseline cardinality). This is the spec's own model; the randomized run order
   spreads any drift effect across io_methods (see §9).

The paper should describe it as a **"TPC-H–based / TPC-H–derived workload"** rather than an
audited TPC-H QphH, and note both deviations above.
